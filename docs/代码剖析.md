# AgentLab 代码剖析

> 本文基于**当前仓库的实际代码**（不是 `technical_architecture.md` 描述的目标态）逐层剖析，并回答一组高频面试题。
> 凡是「设计文档写了但代码还没实现」的地方，本文都会明确标注 **[设计 / 未落地]**，因为面试时把愿景当成果，是最容易被追问翻车的地方。

---

## 0. 一句话定位

AgentLab 是一个跑在个人电脑上的本地 Agent。它的本质是一个**「模型 → 工具 → 模型」的多轮循环**，外面包了一层工具系统、权限审批、多 Agent 会话、MCP 接入、Skill 注入和长期记忆。模型只负责「推理 + 提出工具调用」，**是否执行、怎么执行、要不要审批，全部由本地 Runtime 决定**——这是整个项目的安全立足点。

---

## 1. 分层结构（对照实际代码）

代码实际落地的分层如下。括号里是真实存在的文件。

```
L1 交互层      app/cli.py（REPL、斜杠命令、流式渲染、审批菜单）
                └─ 设计中还有 TUI / Web UI，目前主力是 CLI

L2 Runtime层   app/agent/runtime.py     AgentSession —— CLI 当前主路径，单轮工具循环
                app/agent/orchestrator.py Orchestrator —— Planner+Executor+Replanner 编排路径
                app/agent/{planner,executor,replanner}.py
                app/agent/tasks.py       TaskStore —— 任务状态唯一可信源
                app/agent/approval.py    审批策略
                app/agent/cancel.py      协作式取消
                app/agent/events.py      RunEvent 事件协议
                app/agent/session_router.py 多 Agent 会话切换
                app/agent/profiles.py    AgentProfile

L3 能力层      app/tools/registry.py    ToolRegistry + Tool
                app/tools/builtin/*      内置工具
                app/mcp/*                MCP 接入
                app/skills/*             Skill 加载与注入
                app/memory/__init__.py   长期记忆策略

L4 适配器层    app/models/router.py     ModelRouter
                app/models/{anthropic,openai,compatible}_adapter.py
                app/models/protocol.py   ModelResponse / ToolCall / ToolResult

L5 资源层      本地/云端模型、workspace 文件、MCP Server、SQLite(data/agentlab.db)
```

各层职责一句话：

| 层 | 职责 | 不做什么 |
|---|---|---|
| L1 交互层 | 收输入、渲染事件、弹审批菜单 | 不做任何 Agent 决策 |
| L2 Runtime | 持有会话/历史/任务，驱动循环，管审批和取消 | 不直接调模型 SDK、不直接碰底层库 |
| L3 能力层 | 把「工具/MCP/Skill/记忆」统一成可调用能力 | 不决定是否放行（交给审批） |
| L4 适配器层 | 把三家 provider 的差异翻译成内部统一协议 | 不持有业务逻辑 |
| L5 资源层 | 模型、文件、外部 server、数据库 | —— |

**关键原则**：上层只依赖下一层的抽象。Runtime 只认 `ModelResponse`/`ToolCall`，不认 Anthropic 或 OpenAI 的原生对象——这样换模型不动业务逻辑（`app/models/protocol.py`）。

### Q1. Agent Loop 主循环：你的 Agent 怎么知道任务做完了？

**问题本质**：循环的终止条件是什么？是硬编码「完成指令」，还是用协议层的隐含约定？

**代码现状（`app/agent/runtime.py:141-216`）**

终止判断只有一行，是整个循环的灵魂：

```python
for _ in range(self.max_steps):
    resp = self.llm.create_message(messages=self.messages,
                                   tools=self.tools.schemas() or None, ...)
    self.messages.extend(resp.provider_payload)
    ...
    if not resp.tool_calls:        # ← 终止条件
        return resp.text
    # 否则：执行工具 → 把结果塞回 messages → 进入下一轮
```

循环靠两件事收口：

1. **协议层隐含约定**：模型这一轮**没有返回 `tool_use`**（`resp.tool_calls` 为空），就视为「我不需要再做动作了，这是最终回答」。模型还要调工具，就一定带 `tool_use` 块；不带，就是说完了。Executor 路径里注释写得很直白：`# 没有工具调用 = 模型认为这个子任务已经做完`（`executor.py:104`）。
2. **硬边界兜底**：`max_steps`（默认 8）防止模型陷入「调工具→看结果→再调」的死循环烧钱。耗尽返回 `(达到最大步数仍未给出最终答案)`。

**为什么这比硬编码「完成指令」优雅**

- 不需要约定一个 `<task_done>` 之类的魔法 token，也不需要让模型每轮自报「我做完了吗」。完成与否**内生于 Function Calling 协议本身**：有动作就调工具，没动作就出文本，二者互斥。
- 不依赖模型「听话地」输出特定格式——小模型经常不听话，但「调不调工具」这个信号是 provider 在协议层给的，比让模型自己声明可靠得多。
- 状态机极简：循环只有「有 tool_use → 执行」和「无 tool_use → 返回」两个分支。

**面试怎么讲**

> 我没有让模型自己喊「完成」，而是用 Function Calling 协议的隐含语义来判定。每一轮模型要么返回 tool_use 块（还要做动作，我执行完把结果喂回去继续循环），要么只返回文本（不再需要动作，这就是终态，直接返回）。终止条件就是 `if not tool_calls: return`。这样完成判定不依赖模型输出任何约定格式，而是落在协议层——对不听话的小模型尤其稳。另外我有 max_steps 硬上限兜底防死循环。

可追问的延伸点：编排路径（Orchestrator）下，单任务的「做完」同样是「无 tool_use」（`executor.py:105`），但**整个 run 的「做完」**是另一层——由 TaskStore 判定，见 Q9。

### Q2. 工具系统设计：核心工具怎么设计？Function Calling 协议是什么？输入输出怎么规范？

**先纠正一个常见预设**：AgentLab **不是** Claude Code 那套 `ReadFile/WriteFile/EditFile/Bash/Glob/Grep`。实际注册的内置工具是：

| 工具 | 文件 | 风险 | 说明 |
|---|---|---|---|
| `read_file` | `builtin/files.py:99` | 只读 | 读文本，>200KB 截断 |
| `write_file` | `builtin/files.py:114` | **需审批** | 整文件覆盖写（没有局部 Edit，全量覆盖） |
| `list_dir` | `builtin/files.py:130` | 只读 | 列目录，目录名带 `/` |
| `code_search` | `builtin/code_search.py` | 只读 | 4 种模式 text/regex/file/symbol，相当于 Grep+Glob 合一 |
| `shell` | `builtin/shell.py` | **需审批** | 执行命令，相当于 Bash；Unix 走 bash、Windows 走 PowerShell |
| `todo_write` | `builtin/todo.py` | 只读(改内存) | 模型维护任务清单，CLI 实时渲染 |

> 面试如果对方按 Claude Code 的 6 工具问，要主动说清差异：**我没有独立的 Edit/Glob/Grep——Grep 和 Glob 合并进 `code_search` 的 4 个 mode，Bash 就是 `shell`，写文件目前是全量覆盖没有 patch 式 Edit。** 这是诚实加分项，硬凑会被识破。

**Function Calling 协议是什么（`app/models/protocol.py`）**

它是「模型和程序之间用结构化 JSON 互相喊话」的约定，三个数据结构构成内部统一协议：

```python
@dataclass
class ToolCall:      # 模型 → 程序：我要调这个工具
    id: str          # provider 分配，回传结果要对上
    name: str        # "read_file"
    arguments: dict  # {"path": "README.md"}

@dataclass
class ToolResult:    # 程序 → 模型：工具执行结果
    tool_call_id: str
    output: str
    is_error: bool

@dataclass
class ModelResponse: # adapter 翻译后给 Runtime 的统一响应
    text: str
    tool_calls: list[ToolCall]
    provider_payload: Any   # provider 原生 content blocks，原样塞回 messages
    ...
```

**工具的输入怎么规范**：每个 `Tool` 自带 `input_schema`（JSON Schema），通过 `registry.schemas()` 发给模型，模型据此知道该传哪些字段（`registry.py:35-41`）。例如 `read_file` 声明 `{"path": {"type":"string"}}, required:["path"]`。

**工具的输出怎么规范**：所有工具返回**纯字符串**，由 `ToolRegistry.execute()` 统一兜异常（`registry.py:73-85`）：

```python
def execute(self, name, args) -> tuple[str, bool]:
    try:
        return tool.executor(args or {}), False
    except Exception as exc:
        return f"{type(exc).__name__}: {exc}", True   # 不抛，错误也变成给模型看的文本
```

**这里有个关键设计决策**：工具出错**不抛异常**，而是把错误字符串当成正常输出返回给模型，`is_error=True`。这样模型能「看到」错误自己决定重试/换方案/告知用户——错误也是上下文的一部分。

**面试怎么讲**

> 工具系统的核心是一个 `Tool` dataclass（name + description + JSON Schema 的 input_schema + executor + requires_approval）和一个 `ToolRegistry`。Function Calling 的协议我抽象成三个内部结构：ToolCall（模型要调什么）、ToolResult（执行结果）、ModelResponse（统一响应）。Runtime 只认这三个，不认任何 provider 的原生格式——换模型零成本。输入用 JSON Schema 约束让模型知道传什么参数；输出统一成字符串，而且工具报错不抛异常而是把错误文本喂回模型，让模型自己消化错误。这套设计让加一个新工具只需注册一个 Tool 实例，不碰循环逻辑。

### Q3. System Prompt 工程：性格和行为边界怎么定义、怎么迭代？

**代码现状（`app/agent/runtime.py:15-56`）**

`DEFAULT_SYSTEM_PROMPT` 这段提示词本身就是一部「迭代故事」，注释里把每条规则的来由都写了，这是讲故事的好素材：

```python
DEFAULT_SYSTEM_PROMPT = """你是 AgentLab,一个本地编码助手。
【行为准则——最重要】
- 主动调查,不要反问。用户让你"看项目"时,直接用工具读明白再回答,
  绝不要回一句"请问你想了解什么"...
- 找代码用 code_search,不要用 shell 拼 grep/find...
- 不要重复你上一条已经说过的话...
"""
```

可以讲的迭代点（都能从代码反推）：

1. **「主动调查不要反问」**——最早模型遇到「看下这个项目」会回「请问你想了解什么」。于是把「先调查后结论」拉到准则第一条。
2. **注入工作目录**（`build_system_prompt()`，`runtime.py:42-56`）：注释直说——「小模型 qwen2.5-coder:7b 不会凭空知道自己在哪个目录，用户说『看下当前项目』时会反问『项目在哪』」。解法是把 workspace 根目录显式写进 prompt。这是一个非常具体、非常真实的「迭代故事」。
3. **「找代码用 code_search 不要拼 grep」**——引导模型走低风险只读工具，而不是动不动调高风险的 shell。
4. **「User denied execution 不要立即重试」**——配合审批被拒后的行为约束。
5. **浏览器工具的操作顺序**（navigate→snapshot→用 ref 操作）——避免模型凭空猜 CSS selector。

**面试怎么讲**

> System Prompt 是 Agent 的性格和行为边界，我把它当代码一样迭代，每条规则都对应一个踩过的坑。举个最具体的：本地小模型不知道自己的工作目录，用户说「看下当前项目」它会反问「项目在哪」。我的解法是运行时把 workspace 绝对路径动态注入 prompt（build_system_prompt），模型就能直接 list_dir 而不反问。还有一条「主动调查不要反问」是我把它顶到准则第一位的——Agent 的体验差异，一半在这份提示词里。迭代方式是：观察到一类坏行为 → 加一条针对性规则 → 看是否收敛。

### Q4. 权限系统：怎么给 Agent 装安全刹车？分级设计怎么平衡能力与失控？

**这里必须区分设计和实现，否则会被追问穿帮。**

**[设计 / 部分未落地]** `technical_architecture.md §7.6` 设计了 9 级风险分类（read/observe/network/write/browser_control/desktop_control/remote_execute/execute/destructive）。

**代码实际实现的，是一个更朴素但能跑的方案**：

1. **二元风险标记**（`registry.py:33`）：每个 `Tool` 只有一个 `requires_approval: bool`。只读工具（read_file/list_dir/code_search）为 `False`，写/执行类（write_file/shell/terminal_*）为 `True`。
2. **审批策略接口**（`approval.py`，用 `Protocol` 鸭子类型）：
   - `AutoApprove`——无条件放行（`-y` 参数 / CI）
   - `DenyAll`——无条件拒绝（测试、只读模式）
   - `InteractivePolicy`——方向键菜单，三选项：**允许这次 / 本会话总是允许该工具 / 拒绝**（`approval.py:89-126`）
3. **会话级白名单**（`approval.py:91`）：选了「总是允许」的工具名进 `self._always` set，后续不再问——这是「能力 vs 失控」平衡的核心机制：高频工具批一次就免打扰，但白名单只在本会话有效，重启清零。
4. **拒绝的处理**：被拒不是抛错，而是给模型回 `DENIED_MESSAGE`「User denied execution... Do not retry without confirming」（`runtime.py:58`），并配合 system prompt 让模型别犟着重试。
5. **workspace 边界**（`files.py:28-42`）：所有文件路径 `resolve()` 后校验必须在 `workspace_root()` 之下，越界直接 `refused`——这是一道不依赖审批的硬墙。
6. **MCP 工具的审批继承**：MCP 工具默认也要审批，只有列入 server `auto_approve` 白名单的才豁免。

**怎么平衡能力与失控（这是答题重点）**

- 默认安全：写/执行**默认要批**，只读默认放行——降低高频操作的摩擦，同时守住有副作用的动作。
- 会话级白名单：把「每次都问」的烦人程度，和「一次性全放开」的失控风险，折中成「这个工具本会话内信任」。
- 多道独立防线：审批是一道，workspace 边界是另一道（即使审批放行也越不了界），模型无法自我提权。
- 拒绝即上下文：拒绝反馈给模型而非崩溃，Agent 能优雅降级。

**面试怎么讲（诚实版）**

> 我在设计文档里规划了 9 级风险分类，但代码目前落地的是一个更务实的版本：工具上一个 requires_approval 布尔 + 可插拔的审批策略（Auto/Deny/Interactive）。刹车的关键有三层：第一，只读默认放行、有副作用的默认拦截审批；第二，交互审批给「允许这次/本会话总是允许/拒绝」三档，高频工具批一次进会话白名单免打扰，但重启就清零，不会永久放权；第三，workspace 路径边界是一道独立于审批的硬墙，越界直接拒，模型没法自我提权。能力和失控的平衡点就在「会话级白名单」——既不每次烦死用户，也不一次性把权限全交出去。下一步是把布尔风险升级成分级 enum，按等级配差异化策略。

### Q5. MCP 协议：为什么不自己造工具调用的轮子，而是接 MCP？外部生态怎么打通？

**问题本质**：内置工具已经能用了，为什么还要 MCP？

**代码现状（`app/mcp/{manager,adapter,config}.py`）**

- **MCPManager**：在后台线程跑一个 asyncio 事件循环，连接 stdio MCP server，通过 `run_coroutine_threadsafe` 做同步↔异步桥接。每个 server 在自己的 `_serve()` task 里维持 `stdio_client + ClientSession` 上下文存活（保持会话状态）。
- **MCPAdapter**：把 MCP 发现的工具**包装成和内置工具一样的 `Tool` 对象**注册进同一个 `ToolRegistry`。对 Runtime 来说，MCP 工具和内置工具**长得完全一样**——这是打通生态的关键：循环不需要知道一个工具是本地实现还是远程 MCP server 提供的。
- **名字防撞**：内置工具（read_file 等）不能被 MCP 覆盖，撞名警告并跳过。
- **安全**：`env_allowlist` 限制传给子进程的环境变量（默认只 `PATH`）；新 server 默认 `enabled: false`；输出经 `redact()` 脱敏。
- **已打通的实例**：通过 Playwright MCP 拿到浏览器控制能力（navigate/snapshot/click/type），**自己一行浏览器代码没写**，直接接别人的 MCP server。

**为什么接 MCP 而不自己造**

1. **标准化**：MCP 是 Anthropic 推的开放协议，工具发现（`list_tools`）、调用（`call_tool`）、传输（stdio / Streamable HTTP）都有现成标准。自己造等于发明一套没人用的私有协议。
2. **生态复用**：GitHub、数据库、浏览器、IDE-LSP 已经有大量现成 MCP server。接进来就有，不用为每个外部系统写一遍 adapter。Playwright 浏览器控制就是活例子。
3. **进程隔离**：外部工具跑在独立子进程，崩了不拖垮主进程；环境变量白名单限制它能看到什么。
4. **统一审批**：MCP 工具映射成 `ToolDescriptor` 后，**继承同一套风险/审批机制**，外部工具不会绕过本地安全策略。

**面试怎么讲**

> 内置工具解决「应用进程内的原子能力」，MCP 解决「怎么接外部系统的工具生态而不重复造轮子」。我不自己造工具调用协议，是因为 MCP 已经是开放标准，工具发现、调用、传输都定义好了，而且 GitHub/数据库/浏览器有大量现成 server。我的 MCPAdapter 把 MCP 工具包装成和内置工具一模一样的 Tool 注册进同一个 registry——对主循环完全透明，它不知道也不关心这个工具是本地的还是远程 server 的。最实在的收益：我的浏览器控制能力是直接接 Playwright MCP server 拿到的，自己没写一行浏览器自动化代码。外部进程还天然隔离、环境变量白名单管控、统一走我的审批,不会绕过本地安全边界。

### Q6. Skill 系统：MCP 接外部工具，那 Agent 自己的能力怎么沉淀、复用？

**问题本质**：MCP 是「接别人的工具」，Skill 是「沉淀自己的打法」。两者解决的问题不同。

**代码现状（`app/skills/{loader,catalog}.py`）**

- **Skill 是什么**：一个目录 + 一份 `SKILL.md`（frontmatter 元数据 + Markdown 工作流正文）。元数据含 `name / description / allowed_tools / optional_mcp_servers / triggers / enabled`。
- **加载**：启动扫描 `skills/*/SKILL.md`，解析 frontmatter，生成 `SkillCatalog`。未知来源默认 `enabled: false`。
- **注入**：`build_skill_context()` 把工作流正文**渲染进 system prompt**，告诉模型「这类任务该按什么步骤做」。
- **最关键的安全设计**（`catalog.py` 注释明说）：**Skill 声明的 `allowed_tools` 是「需求」不是「授权」**。能不能真用某个工具，由 AgentProfile.tools + ToolRegistry + 审批策略独立决定。Skill 只能注入「指导文字」，不能开权限。
- **匹配**：`resolve()` 合并三个来源——AgentProfile 显式启用的、全局启用的、通过 `triggers` 自动匹配的。

**Skill / Tool / MCP 三者区别（一定要讲清，是高频对比题）**

| 概念 | 解决的问题 | 例子 |
|---|---|---|
| Skill | **怎么做一类任务**（流程/打法/SOP） | 「代码审查先跑测试，再按严重度分级输出 findings」 |
| 内置 Tool | 进程内的**原子能力** | 读文件、写文件 |
| MCP Server | **外部进程/服务**暴露的工具 | GitHub、数据库、浏览器 |

**面试怎么讲**

> Tool 是原子能力（读文件），MCP 是接外部工具生态（GitHub server），Skill 是沉淀「怎么做一类任务」的打法。比如「代码审查」这个 Skill，本质是一段 SOP——先读改动和测试、再按严重度分级输出——写进 SKILL.md 的工作流，启用时注入 system prompt。它复用的是「方法论」，不是「代码」。最重要的一个设计：Skill 里声明的 allowed_tools 只是「这个流程需要这些工具」的声明，绝不等于授权——真正能不能用，还是 AgentProfile 白名单 + 审批说了算。Skill 只能给模型加「指导文字」，不能给它加权限。这条边界守住了，Skill 才不会变成提权后门。

### Q7. 上下文窗口管理：对话变长、token 烧钱了怎么办？怎么压缩才能既省钱又不丢关键信息？

**这是最容易翻车的一题，必须诚实。**

**代码现状：上下文压缩 [未落地]**

逐文件确认过，当前**没有任何上下文压缩 / 截断 / 摘要逻辑**：

- `AgentSession.chat()` 的循环里，`self.messages` 只增不减——每轮把 `resp.provider_payload` 和工具结果不断 `extend` 进去（`runtime.py:173, 214`），**没有任何裁剪**。
- `max_steps`（默认 8）限的是**工具循环的轮数**，不是 token / 上下文长度。
- 唯一和「上下文体积」沾边的，是**单个工具输出层面**的截断：`read_file` 200KB 上限（`files.py:21`）、shell/code_search 输出有字符上限。这是**入口减负**，不是历史压缩。
- 结果：长对话会无限增长，直到撞 provider 的上下文上限。目前唯一硬止损是 provider 自己的报错。

**已有的设计（`technical_architecture.md §7.3`，代码未落地）**

虽然代码还没写，但设计文档已经把这套方案定义得相当完整，分三个组件落在 `app/agent/`：`context.py`（组装）+ `context_budget.py`（算预算/定阈值）+ `context_compaction.py`（生成/校验摘要）。面试时把这套讲出来，等于「没实现但想透了」。

**① 上下文怎么组装（§7.3.1）**——每次调模型前按固定顺序拼，从「钉死不动」到「可压缩」依次是：

```
System Prompt   ← 角色/安全规则，固定预算
Active Task     ← TaskStore 当前任务、依赖、完成标准
Skill Context   ← 匹配到的 Skill 工作流
Tool Snapshot   ← 可用工具 schema
Memory Context  ← 长期记忆，标注 scope/source
Context Summary ← ★压缩摘要：旧历史被折叠成这一段
Recent Messages ← ★最近消息原文（含未闭合的 tool_call/tool_result）
Evidence Refs   ← 大文本/截图/长输出只放引用，不放原文
```

关键边界（§7.3.1 末）：**压缩只替换「模型输入里的旧片段」，绝不删原始消息/审计/观察记录**。原文照样落 SQLite，压缩动的只是「这一轮喂给模型看什么」。

**② 什么时候压（§7.3.2 ContextBudget）**——按当前模型 profile 的窗口算预算，分项预留（reserved_output / system_and_tools / memory / summary / recent_messages / evidence），按比例触发：

| 触发点 | 动作 |
|---|---|
| 预计输入 > 窗口 **70%** | 发 `context_budget_warning`，下个稳定点准备压 |
| 预计输入 > 窗口 **85%** | 下次调模型前**强制压缩**旧历史 |
| 切到上下文更小的模型 | 重算预算，压到新窗口能接受 |
| 复杂 run 完成���历史猛涨 | 后台生成 session summary，降下一轮延迟 |
| `/session switch` / 恢复会话 | 只加载「最近 summary + recent」，不全量回放历史 |
| 用户手动 `/context compact` | 立即压 |

阈值用「窗口百分比」而不是写死 token 数，所以换大窗口/小窗口模型都自适应。

**③ 压成什么（§7.3.3 结构化摘要）**——这是设计里最值得讲的一点：**摘要不是自由散文，是结构化 YAML**，强约束模型「哪些信息必须留」：

```yaml
summary:
  user_goal:          # 当前目标 + 成功标准
  active_constraints: # 用户明确的约束/禁止/偏好
  decisions:          # 已确认的设计决定及原因
  current_state:      # 代码/网页/任务当前状态
  open_tasks:         # 未完成任务、阻塞原因、下一步
  tool_evidence:      # [{source: tool_execution_id, finding: 可复用结论}]
  files_and_artifacts:# 涉及的文件/截图/下载
  failed_attempts:    # ★已失败的方案，避免重复踩坑
  approvals_and_risks:# 已授权范围、被拒动作、高风险提示
  memory_candidates:  # 可能写长期记忆的候选（不自动落库）
  handoff_note:       # 给后续调用的交接说明
```

每条摘要还带元数据：`source_message_range`、`source_run_ids`、`token_count_before/after`（可量化压缩比）、`compression_model_profile`、`created_at`。引用工具结果/截图时**只放 evidence id / content ref，不把大内容重塞回去**。

**④ 哪些绝不能压（§7.3.5 安全边界）**——这是「既省钱又不丢关键信息」的核心答案：

- **当前未完成 run、最后一条用户请求、pending approval、未闭合的 tool_call/tool_result 对**——绝不压（压了就破坏协议正确性）。
- 压缩不能改审计事实：审批/工具参数/结果摘要/错误必须保留结构化记录。
- 摘要进云端模型前走和普通上下文一样的脱敏 + 数据边界提示；敏感 session 可强制用本地小模型做摘要。
- **摘要不自动写长期记忆**——只有 `memory_candidate` 经 MemoryPolicy 确认才入库（这条直接接 Q8）。
- 摘要必须**保留不确定性**：拿不准的标 `unknown/unresolved`，不许为缩短上下文编结论。
- 压缩失败时降级：`context_compaction_failed`，退回「只留最近原文尾巴」或提示用户换大窗口模型，绝不硬塞超限。

**与长期记忆的边界（§7.3.6）**——别混为一谈：Context Summary 默认**不跨 session**，只为「让这一段长对话在有限窗口内继续」；要跨 session 的是 Long-term Memory（user/agent/workspace）。两者唯一的接口是 `memory_candidate`——摘要可以提名候选，但必须经记忆策略确认才落库。

**面试怎么讲（诚实 + 设计透彻）**

> 先说实现状态：代码目前**只做了入口减负**（read_file 200KB、shell/code_search 输出截断），防止单次塞爆，但 messages 历史只增不减——**历史压缩还没落地**，是我清楚知道的核心待补项。
>
> 但设计我想透了，分三块。**何时压**：按当前模型窗口算 ContextBudget，输入到 70% 发预警、85% 强制压，阈值用窗口百分比所以换模型自适应。**压成什么**：不是让模型随便总结，而是输出一个**结构化 YAML 摘要**——强制保留 user_goal、active_constraints、decisions、open_tasks、tool_evidence，还专门有 failed_attempts 避免重复踩坑、approvals_and_risks 记住授权边界。每条摘要带 token_before/after 可量化、带 source_range 可回溯，引用大内容只放 evidence id 不重塞原文。**哪些绝不动**：当前未完成的 run、最后一条用户请求、未闭合的 tool_call/tool_result 对——压这些会直接破坏协议正确性。
>
> 「既省钱又不丢关键信息」的本质就是**分区**：固定区（system/task/tool）+ 可压区（旧历史→摘要）+ 保护区（最近消息和未闭合调用），压缩器只能动可压区。再加两条安全约束：摘要要标不确定性不许编、不自动写长期记忆，跟长期记忆的边界划清楚。

> 加分细节：代码里 `cumulative_usage` 已经在累加 input/output token（`runtime.py:161-164`），这正是 ContextBudget 算「预计输入」的数据源——触发逻辑接上去就能用，地基已经留好了。

### Q8. 记忆机制：跨会话记忆 vs 上下文记忆的本质区别？短期/长期/项目级怎么分层？怎么避免「刚注入就被压缩掉」？

**问题本质**：「记忆」是个被滥用的词，要先拆清楚两种东西。

**本质区别（先讲这个）**

| | 上下文记忆（context） | 跨会话记忆（long-term memory） |
|---|---|---|
| 载体 | `self.messages` 列表（内存） | SQLite `memories` 表（磁盘） |
| 生命周期 | 单次会话，结束即丢 | 跨会话持久，重启还在 |
| 进入模型的方式 | 直接就是 messages | 检索后**注入 system prompt** |
| 本质 | 模型「现在看得见」的对话 | 需要主动「想起来」并塞进上下文的知识 |

一句话：**上下文记忆是「工作记忆」，跨会话记忆是「需要被检索召回的知识库」。** 长期记忆不会自动出现在模型眼前，必须显式检索再注入——这是两者最本质的差别。

**代码怎么分层（`app/memory/__init__.py` + `app/storage/__init__.py`）**

跨会话记忆**真的持久化进了 SQLite**（不是内存假装），`memories` 表带 `scope` 字段做分层（`storage/__init__.py:51-61`）：

| scope | 含义 | 代码状态 |
|---|---|---|
| `user` | 用户长期偏好 | scope 已支持 |
| `agent` | 某 Agent 的经验 | scope 已支持 |
| `workspace` | 项目级事实 | scope 已支持 |
| `session` | 当前会话摘要 | `ReadWriteMemory.save()` 实际写的就是这个 |

策略接口分三档（`memory/__init__.py`）：
- `NoMemory`——不用（默认）
- `ReadMemory`——会话开始检索注入，不写
- `ReadWriteMemory`——检索 + 会话结束把最后 6 轮摘要写进 `memories`（`memory/__init__.py:46-68`）

**检索是 SQLite LIKE 全文匹配**（`storage/__init__.py:203-221`），**没有向量/embedding**——MVP 级，注释自己也写了「足够 MVP 使用」。

注入：`inject_memories()` 把检索到的记忆拼成 `【相关记忆】` 块追加到 system prompt 末尾（`memory/__init__.py:81-86`）。

**「刚注入的长期记忆下一步就被压缩掉」这个 bug 怎么避免**

这题很尖，本质是 **Q7 的压缩逻辑和 Q8 的注入逻辑会打架**：长期记忆注入在 system prompt 里，如果压缩时把 system prompt 也一起裁了，记忆就丢了。

- **当前代码不会触发这个 bug**——因为根本没做压缩（Q7），而且记忆是注入在 **system prompt** 而不是 messages 历史里，system prompt 每轮都完整重发（`runtime.py:156`），不会被「历史裁剪」碰到。
- **但一旦实现压缩，就必须防**：解法是给上下文内容**分优先级/分区**——system prompt 和注入的长期记忆标记为「钉住（pinned），永不压缩」，压缩器只能动「历史对话」区。换句话说，注入的记忆不能混进可被裁剪的 messages 流，要放在受保护的区域。

**面试怎么讲**

> 先拆概念：上下文记忆是 messages 里的工作记忆，会话结束就没了；跨会话记忆是落到 SQLite 的知识，要主动检索召回再注入 system prompt。本质区别是「自动看得见」vs「要被想起来」。我用一个 memories 表，靠 scope 字段分 user/agent/workspace/session 四层——用户偏好、Agent 经验、项目事实、会话摘要。策略分 none/read/read_write 三档，read_write 会在会话结束把最近几轮摘要写库。坦白讲检索目前是 SQLite LIKE 匹配，没上向量，是 MVP。
>
> 「刚注入就被压缩掉」这个坑很真实——它本质是压缩逻辑和注入逻辑打架。我的防法是：长期记忆注入在 system prompt 而不是 messages 历史里，而 system prompt 每轮完整重发、属于「钉住不压缩」的受保护区，压缩器只能动历史对话区。注入的记忆绝不能混进会被裁剪的消息流。当前因为我还没做压缩，这个 bug 暂时不会触发，但实现压缩时分区保护是第一要务。

### Q9. 多 Agent 协作：SubAgent / Worktree / Agent Teams 各解决什么？什么时候用哪个？为什么不能一套机制吃下所有场景？

**又是必须诚实的一题。**

**代码现状**

- **已实现的是「多会话切换」，不是「多 Agent 并行协作」**。`SessionRouter`（`session_router.py`）支持创建/切换/归档/删除会话，每个会话绑一个 `AgentProfile`，有独立 messages、TaskStore、长期记忆作用域，**持久化进 SQLite 可恢复**。但同一时刻**只有一个 active session**——是「串行切换」，不是「并行协作」。
- **SubAgent / Worktree / Agent Teams 这三套机制：代码里完全没有**。全仓搜不到 spawn_agent / fork / worktree 隔离 / 团队层级。这是设计愿景，未落地。

**所以这题要答的是「概念辨析 + 我已有的地基」，而不是吹实现。**

三套机制各自解决什么（这是概念题，答清楚就拿分）：

| 机制 | 解决的问题 | 典型场景 | 为什么别的机制吃不下 |
|---|---|---|---|
| **SubAgent** | **上下文隔离 + 任务委派**：主 Agent 把一个子任务丢给一个全新上下文的子 Agent，子 Agent 干完只回结论，不把一堆中间过程污染主上下文 | 「去把这 20 个文件读一遍找出哪个有 bug」——读文件的噪音不该进主对话 | 单 Agent 会被中间过程撑爆上下文（正好是 Q7） |
| **Worktree** | **文件系统隔离**：多个 Agent 在各自的 git worktree（独立工作副本）里改代码，互不踩踏 | 并行让两个 Agent 改同一个 repo 的不同 feature | 共享一个工作目录会互相覆盖文件 |
| **Agent Teams** | **角色分工 + 协同**：多个不同职责 Agent（如 coder + reviewer + tester）协作完成一个大目标 | 写代码的 Agent 产出，审查的 Agent 挑错，测试的 Agent 验证 | 单 Agent 既当运动员又当裁判，质量和客观性都差 |

**为什么不能一套吃下**：三者隔离的**维度不同**——SubAgent 隔离的是**上下文/token**，Worktree 隔离的是**文件系统**，Agent Teams 隔离的是**职责/视角**。一套机制只能解决一个维度的隔离，硬塞会变成「什么都做、什么都不精」。

**我已有的地基（把未落地讲成「有规划且地基已铺」）**

- `AgentProfile`（`profiles.py`）已经支持定义不同职责的 Agent（coding / browser…），各自带工具白名单、模型、记忆策略——这是 Agent Teams 的**角色定义层**已经有了。
- `SessionRouter` 的多会话隔离，是 SubAgent「独立上下文」的雏形——把「切换」改成「主会话 spawn 子会话并回收结论」就能演进成 SubAgent。
- `Orchestrator` 的 Planner/Executor/Replanner 已经能把目标拆成带依赖的任务图——这是「把子任务分给不同 Agent」的调度地基。

**面试怎么讲（诚实版）**

> 这三个机制隔离的维度不一样，不能互相替代：SubAgent 隔离的是上下文——主 Agent 把脏活（比如扫 20 个文件）丢给一个独立上下文的子 Agent，子 Agent 只回结论，不污染主对话，本质是为了不撑爆 token；Worktree 隔离的是文件系统——多个 Agent 在各自 git worktree 里改代码不互相覆盖；Agent Teams 隔离的是职责——coder 写、reviewer 审、tester 测，避免一个 Agent 既当运动员又当裁判。一套机制只能管一个维度的隔离，所以吃不下全部。
>
> 落地情况我说清楚：我目前实现的是**多会话串行切换**（SessionRouter），同一时刻一个 active session，每个会话独立上下文、独立 TaskStore、独立记忆作用域，持久化可恢复。**SubAgent/Worktree/Teams 这三套还没实现**，是路线图。但地基铺好了：AgentProfile 已经能定义不同职责的 Agent，是 Teams 的角色层；多会话隔离是 SubAgent 独立上下文的雏形；Orchestrator 的任务图调度是把子任务分派给不同 Agent 的调度层。从这往下走，SubAgent 是最该先做的——因为它直接解 Q7 的上下文膨胀问题。

## 3. 两条执行路径要分清（容易被追问）

代码里有**两套循环**，面试别混：

| | `AgentSession`（`runtime.py`） | `Orchestrator`（`orchestrator.py`） |
|---|---|---|
| 定位 | **CLI 当前主路径** | 编排路径（测试/未来 UI） |
| 循环粒度 | 一整轮对话，单层工具循环 | Planner 拆任务 → Executor 逐任务 → Replanner 回写 |
| 「完成」判定 | 无 tool_use 即返回（Q1） | 单任务无 tool_use 完成 + 整体由 TaskStore.is_done() 判（Q1 延伸） |
| 任务管理 | 模型用 todo_write 维护扁平清单 | Planner 生成带依赖的任务图，TaskStore 是唯一可信源 |
| 事件 | 简单 `TurnEvent` | 结构化 `RunEvent`（run_started/plan_created/task_updated…） |
| 共享 | 同一套 ModelRouter / ToolRegistry / ApprovalPolicy | 同上 |

**Orchestrator 的整体终止逻辑**（`orchestrator.py:115-156`）比单循环复杂，值得单独记：

```python
while steps_left > 0:
    task = self.store.claim_next()   # 取依赖已满足的 pending 任务
    if task is None: break           # 没有可跑的：要么全完成，要么卡死
    outcome = executor.run_task(...)
    replanner.apply(task, outcome)   # 回写状态，失败时追加补救任务
# 收尾三判定：
#   is_stalled()  → 有未完成任务但没一个能跑（依赖被 failed 卡死）→ run_failed
#   steps_left<=0 且 has_open() → 达到预算上限 → run_failed
#   否则 → run_completed
```

这回答了 Q1 的延伸：**单任务**「做完」靠协议（无 tool_use），但**整个 run**「做完」靠 TaskStore 的状态机（全部任务到终态）。两层终止条件，不要混为一谈。
